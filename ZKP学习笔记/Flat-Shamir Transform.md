## Schnorr Protocol

**Schnorr 协议**是 **Sigma 协议** （Σ-协议）的一个著名例子，这是一种三阶段交互式证明系统，证明者在不泄露秘密的情况下说服验证者知道秘密。在这种情况下，证明器旨在证明对椭圆曲线上某一点的已知信息，而不披露该点本身。

假设一个证明者想要证明其知晓椭圆曲线E上的一个点$a$，其中：

+ $PK = a\cdot G$（其中 $G$ 是椭圆曲线群的生成元，$a$ 是秘密标量，$sk=a$）。

+ 证明者必须说服验证者她知道 $a$，但不透露 $a$。

我们在图1中描述了Schnorr Protocol的工作流程：

![image-20251223181858530](https://raw.githubusercontent.com/hxd77/BlogImage/master/TyporaImage/20251223181905602.png)

1. **Commit Phase**

+ 证明者选择一个随机标量 $r$，并计算 $R = r\cdot G$。
+ 证明者将 $R$（承诺）和 $PK$ 发送给验证者。

2. **Challenge Phase**

+ 验证者选取一个随机的挑战标量 $c$，并将其发送给证明者。

3. **Open Phase**

+ 证明者计算 $z = r + c\cdot sk$（使用她的秘密 $sk=a$）。

+ 证明者将 $z$发送回验证者。

+ 验证者检查是否：$z·G == R + c·PK$

+ 如果等式成立，验证者接受该证明；否则，验证者拒绝该证明。

##为什么这有效?

+ **完备性**：如果证明者知道 $a$，那么她总能计算出一个满足验证方程的有效 $z$。

+ **可靠性**：一个不知道 $a$的作弊证明者，几乎不可能伪造出有效的 $z$。
+ **零知识**：验证者除了知道证明者了解某个事物这一事实外，对该事物一无所知。



## 验证者为什么需要挑战证明者

如果证明者拥有某种神奇的能力，能在承诺阶段之前就知道挑战值 $c$，那么Schnorr Protocol就会变得完全不安全。

如图2所述，如果伪造的证明者预先知道挑战值 $c$，那么该伪造的证明者无需知晓私钥 $a$ 就能预测出 $z$。伪造的证明者计算 $R’=z\cdot G - c\cdot PK$，并将$R^{\prime}$和 $PK$ 发送给验证者，接着验证者向证明者发送挑战值 $c$，然后证明者向验证者发送 $z$，之后验证者检查 $z\cdot G$是否等于 $R’ + c\cdot PK$。显然，该等式是成立的，因此可靠性就失效了！

![image-20251223183213524](https://raw.githubusercontent.com/hxd77/BlogImage/master/TyporaImage/20251223183213564.png)

如果证明者在发送 $R$ 之前就知道挑战 $c$，那么整个协议就会崩溃：

+ 恶意证明者可以在不知道秘密的情况下伪造证明。
+ **操作顺序（commit→challenge→open）**对安全性至关重要。

这就是为什么Schnorr Protocol要求验证者只有在看到承诺后才能发送挑战。



## Non-Interactive Schnorr Protocol

我们已经确定，在交互式 Schnorr 协议中，验证者必须在收到证明者的承诺 $R$ 之后才能发送挑战 $c$。这种顺序对于保持可靠性至关重要——如果证明者能够在对 $R$ 做出承诺之前确定 $c$，他们就可以在不知道密钥的情况下伪造证明。

这就引出了一个重要的问题：当我们通过Fiat-Shamir变换，用哈希输出替代验证者的挑战，从而使协议变为非交互式时，尽管证明者现在可以在计算其承诺后有效地确定挑战，该协议是否仍然安全？

为了实现这一非交互性，Flat-Shamir变换用对承诺的哈希值替代验证者的挑战值 $c$，即 $c = Hash(PK, R)$

非交互式版本的工作原理如下（如图3所示）：

![image-20251223185316055](https://raw.githubusercontent.com/hxd77/BlogImage/master/TyporaImage/20251223185316101.png)

1. **Commit Phase**

+ 证明者生成随机数 $r$，并计算 $R = r·G$

2. **Challenge Phase**

+ 挑战 $c$ 的计算方式为 $c = Hash（PK，R）$
+ 注意：哈希输入中可以包含额外的上下文，例如正在被签名的消息

3. **Open Phase**

+ 证明者计算 $z = r + c·sk$
+ 发送 $PK$ 和证明元组$(R，z)$
+ 验证者重新计算 $c = Hash(PK，R)$
+ 检查是否 $z·G = R + c·PK$



### 为什么这会保持安全

安全性依赖于几个关键的密码学原理：

1. 作为随机预言机的哈希函数：

+ 哈希函数充当着一个可靠且难以预测的“验证器”
+ 尽管证明者在选择 $R$ 之后可以计算出 $c$，但他们无法：
  + 找到能产生有利的 $c$（抗原像性）的 $R$。
  + 在看到 $c$ 后更改 $R$ ，但不破坏哈希（绑定性质）。

2. 计算绑定

+ 要进行欺骗，证明者需要：
  + 首先选择一个想要的 $c$
  + 然后找到 $R$，使得 $Hash(PK，R)= c$
+ 这在计算上对于安全哈希函数来说是不可行的

尽管我们用哈希函数而非验证者来挑战证明者，但该协议仍然保持安全！
